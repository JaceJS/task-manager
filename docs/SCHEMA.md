# Database schema

PostgreSQL 16, running in Docker. Two tables: `boards` and `tasks`.

A row is **active** when `deleted_at IS NULL` and **in trash** when it is set. Deleting from the
app is a soft delete; deleting permanently from the trash is a real `DELETE`.

## How the schema is created

Alembic migrations, checked into `backend/alembic/versions/`. From an empty database:

```bash
docker compose up -d db
cd backend && alembic upgrade head
```

The first migration is written by hand rather than autogenerated, because Alembic does not
detect triggers and is unreliable for partial and expression indexes.

## Table `boards`

| Column       | Type           | Null | Default  | Notes                          |
| ------------ | -------------- | ---- | -------- | ------------------------------ |
| `id`         | `bigint`       | no   | identity | Primary key                    |
| `name`       | `varchar(255)` | no   | -        | Trimmed by the service         |
| `created_at` | `timestamptz`  | no   | `now()`  |                                |
| `updated_at` | `timestamptz`  | no   | `now()`  | Set by the app on every update |
| `deleted_at` | `timestamptz`  | yes  | `NULL`   | Set means the board is in trash |

| Key / constraint            | Definition                            | Why                                                   |
| --------------------------- | ------------------------------------- | ----------------------------------------------------- |
| `pk_boards`                 | `PRIMARY KEY (id)`                    | Row identity                                          |
| `ck_boards_name_not_blank`  | `CHECK (name ~ '\S')`                 | A board must have a name that is not empty or only whitespace |

## Table `tasks`

| Column        | Type           | Null | Default  | Notes                                    |
| ------------- | -------------- | ---- | -------- | ---------------------------------------- |
| `id`          | `bigint`       | no   | identity | Primary key                              |
| `board_id`    | `bigint`       | no   | -        | The board this task belongs to           |
| `title`       | `varchar(255)` | no   | -        | Trimmed by the service                   |
| `description` | `text`         | yes  | `NULL`   | Optional; whitespace-only is stored as `NULL` |
| `status`      | `varchar(20)`  | no   | `'TODO'` | `TODO`, `IN_PROGRESS` or `DONE`          |
| `created_at`  | `timestamptz`  | no   | `now()`  |                                          |
| `updated_at`  | `timestamptz`  | no   | `now()`  | Set by the app on every update           |
| `deleted_at`  | `timestamptz`  | yes  | `NULL`   | Set means the task is in trash           |

| Key / constraint           | Definition                                                              | Why                                                                     |
| -------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `pk_tasks`                 | `PRIMARY KEY (id)`                                                      | Row identity                                                            |
| `fk_tasks_board_id`        | `FOREIGN KEY (board_id) REFERENCES boards(id) ON DELETE RESTRICT`       | A task can never point at a board that does not exist, and a board that still has task rows cannot be deleted permanently |
| `ck_tasks_title_not_blank` | `CHECK (title ~ '\S')`                                                  | A task must have a title that is not empty or only whitespace           |
| `ck_tasks_status_valid`    | `CHECK (status IN ('TODO', 'IN_PROGRESS', 'DONE'))`                     | Only the three known statuses are storable                              |

## Indexes

| Index                      | Definition                                                              | Why it exists                                                            |
| -------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `uq_boards_name_active`    | `UNIQUE INDEX ON boards (lower(name)) WHERE deleted_at IS NULL`         | Two active boards must not share a name, ignoring case. Partial, so a name held by a trashed board becomes available again |
| `ix_tasks_board_id_status` | `INDEX ON tasks (board_id, status)`                                    | Serves the main query (tasks of one board, optionally filtered by status), the trigger's lookup of active tasks, and the `RESTRICT` check on permanent delete. PostgreSQL does not index foreign key columns automatically |

No other indexes were added. The trash listing is small and rarely opened, so it reads the
tables directly.

## Triggers

Soft delete is an `UPDATE`, so a foreign key cannot police it. These two triggers are the
database-level equivalent, and both raise `restrict_violation`, the same SQLSTATE that
`ON DELETE RESTRICT` raises.

| Trigger                                    | Fires on                                                       | Rejects                                                     |
| ------------------------------------------ | -------------------------------------------------------------- | ----------------------------------------------------------- |
| `trg_boards_block_trash_with_active_tasks` | `BEFORE UPDATE OF deleted_at ON boards`, when it goes from NULL to a value | Moving a board to trash while it still has active tasks |
| `trg_tasks_block_inactive_board`           | `BEFORE INSERT OR UPDATE OF board_id, deleted_at ON tasks`, when the task is active | Creating or restoring an active task on a board that is in trash |

`trg_tasks_block_inactive_board` reads the board row with `FOR SHARE`. That lock makes the rule
hold even when one request creates a task while another moves the same board to trash.

The service layer checks the same rules first, so the user gets a clear message. The database
is the final guard: it also stops direct SQL and concurrent requests.

## Timestamps

`created_at` defaults to `now()`. `updated_at` and `deleted_at` are written with
`clock_timestamp()`, the time the statement runs. `now()` returns the time the transaction
started, which would make two changes inside one transaction look simultaneous.

## A decision considered and rejected

Storing `status` as a native PostgreSQL `enum` type was considered and rejected. Changing the
list later means `ALTER TYPE`, removing a value means recreating the type, and Alembic does not
detect changes to enum values, while a `varchar` with a `CHECK` constraint rejects bad data just
as firmly and can be changed in one migration. A separate status lookup table was rejected for
the same reason: three fixed values do not justify a join.

## Proof that the database enforces the rules

Run against the database directly, with no application code involved:

| Attempt                                                      | Result                                                     |
| ------------------------------------------------------------ | ---------------------------------------------------------- |
| `INSERT` a task with `board_id = 999999`                      | `violates foreign key constraint "fk_tasks_board_id"`      |
| `INSERT` a board named `''` or `'   '`                        | `violates check constraint "ck_boards_name_not_blank"`     |
| `INSERT` a board named `'onboarding'` when `'Onboarding'` is active | `duplicate key value violates unique constraint "uq_boards_name_active"` |
| `INSERT` a task with `status = 'ABC'`                         | `violates check constraint "ck_tasks_status_valid"`        |
| `UPDATE` a board's `deleted_at` while it has active tasks     | `board 1 still has active tasks`                           |
| `DELETE` a board that still has task rows                     | `violates foreign key constraint "fk_tasks_board_id" on table "tasks"` |
| `INSERT` an active task on a trashed board                    | `board 1 is in trash`                                      |
| `UPDATE` a task's `deleted_at` to NULL while its board is in trash | `board 1 is in trash`                                 |
| Reuse the name of a trashed board                             | Succeeds                                                   |

The four rules that matter most (fake `board_id`, hard delete of a board with task rows, trashing
a board with active tasks, an active task on a trashed board) are also automated tests in
`backend/tests/test_database_rules.py`. They run plain SQL, with no application code involved.
